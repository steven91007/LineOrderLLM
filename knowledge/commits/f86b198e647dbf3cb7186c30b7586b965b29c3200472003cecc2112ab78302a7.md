# a0e110e feat: DSPy 多訂單判斷邏輯優化

## Summary
Redefines 'multiple orders' as multiple distinct receivers or addresses rather than multiple products: OrderTypeSignature's docstring and output description state the rule, MultiOrderParser's prompt adds the definition, and OrderTypeClassifier's heuristic now counts occurrences of receiver/address/phone keywords and numbered-list markers instead of literal '訂單1'-style tokens. OrderHandler now defaults client_type to 'dspy' and constructs DSPyOrderClient from the OpenAI key alone. pyproject.toml adds dspy and mlflow, and mlruns/ is ignored.

## Why
The classifier was treating one recipient with several products as multiple orders; the message states that one receiver plus one address plus many items must be a single order.

## Risks
OrderHandler now ignores its dspy_api_key, dspy_model and dspy_max_retries arguments, so DSPY_MODEL and DSPY_MAX_RETRIES from config no longer take effect and the client falls back to its built-in defaults. Changing the default client_type to 'dspy' in the handler is moot when main.py passes ORDER_CLIENT_TYPE, but changes behaviour for any other caller. mlflow is added as a dependency before any code uses it. pyproject requires dspy>=2.6.27 while requirements.txt still pins dspy-ai==2.4.9, and dspy_client.py still uses the legacy dspy.OpenAI API that newer DSPy removes.
